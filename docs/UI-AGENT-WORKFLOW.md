# 案齐 UI 设计系统与 Agent 协作计划

> 状态：执行计划，2026-10-12
>
> 目标：让没有专职 UI 设计师的团队，也能持续产出尺寸、间距、对齐和状态一致的页面。

## 1. 先确认现状

案齐已经有设计系统的基础，不需要引入前端框架或重做一套 UI：

- 前端是原生 HTML/CSS/JavaScript，没有构建步骤。
- `docs/DESIGN-TOKENS.md` 是 UI 规范源，`public/css/style.css` 是实现事实源。
- `style.css` 分为两层：层 A 是三套皮肤共用的布局骨架，层 B 是 `pro`、`paper`、`jade` 的材质变量。
- 页面共用大量已有骨架类，设计令牌文档已经有组件清单、三皮肤零位移约束和 390px 窄屏约束。
- `tools/qa-finance-ui.js` 已经提供了一个可复用的 UI QA 形态：1440px / 390px、三种皮肤、无横向溢出、触控尺寸和交互检查。

因此本计划解决的是协作和执行问题：把现有规范变成 agent 可查、可改、可验收的流程。

## 2. 设计规则的优先级

agent 遇到冲突时按下面的顺序判断：

1. 产品语义和真实使用场景：信息是否清楚、动作是否可完成、风险状态是否可见。
2. `docs/DESIGN-TOKENS.md`：颜色、字号、间距、皮肤和骨架规则。
3. `public/css/style.css`：当前运行代码；若与规范冲突，修复时同时更新规范和代码。
4. 本文件和组件目录：组件的 DOM 结构、状态、响应式行为和验收方式。
5. 页面局部样式：只有在确认它属于页面独有语义时才允许增加。

任何 agent 都不能因为当前页面看起来方便，就新增一个近似的按钮、标签、卡片或间距值。先查已有组件；确实缺少时，先补组件契约，再改页面。

## 3. Agent 角色

这些是工作角色，不要求真的创建固定名称的机器人。一次任务可以由同一个 agent 承担多个角色，但每个角色的产物要留下来。

### UI 盘点 agent

负责把截图或页面问题变成可复现的问题记录，不直接顺手改 CSS。需要记录：

- 页面、路径、皮肤、视口尺寸和复现步骤；
- 期望表现与实际表现；
- 影响范围：单个页面、同一组件，还是全站基础规则；
- 可能的 DOM 类名和 JS 钩子；
- 截图或浏览器测量结果。

### UI 规则 agent

负责决定问题应该落在哪一层：令牌、共享组件、业务模式还是页面。它维护 `DESIGN-TOKENS.md` 和组件契约，避免多个 agent 同时发明不同的尺寸和颜色。

涉及 `style.css` 层 A、层 B、令牌或共享组件时，同一时间只允许一个 agent 修改；其他 agent 先提交问题和建议。

### 组件实现 agent

根据已确认的组件契约修改 HTML/CSS/JS。它不能通过局部 `margin`、`top`、`transform` 或重复颜色值掩盖组件结构问题，也不能删除现有 JS 依赖的 DOM 钩子。

### 页面迁移 agent

只负责把一个页面接入已存在的组件。它可以调整页面数据排列和内容优先级，不能为页面重新定义按钮、标签、表格或卡片的视觉规则。

### 视觉验收 agent

在三套皮肤、桌面和 390px 窄屏下运行页面，检查截图、布局测量、横向溢出、控件高度、键盘焦点、空态和长文本。它只报告证据和失败项，不能在验收时偷偷改代码。

### 门禁 agent

运行 `npm run check` 和页面专用 QA；确认规范文档、组件目录和代码在同一变更中更新。门禁通过后才算完成。

## 4. 组件分层和第一批目录

组件目录建议单独维护为 `docs/UI-COMPONENTS.md`。每个组件都记录：用途、DOM 骨架、允许的类名、尺寸、状态、引用的令牌、响应式规则、JS 钩子、示例页面和禁止用法。

第一批按下面的顺序整理，优先覆盖截图中出现频率最高的东西：

| 层级 | 组件 | 处理内容 |
|---|---|---|
| 基础 | 间距、排版、颜色、边框、圆角、焦点 | 只使用已有令牌；发现缺口时先补语义槽位 |
| 基础元件 | `.btn`、`.chip`、`.pill`、`.dot`、输入框、`details` | 统一高度、内边距、文字行高、禁用/焦点/错误状态 |
| 容器 | `.panel`、`.card`、`.p-head`、`.p-foot`、`.row` | 统一标题、内容区、脚部和分隔关系 |
| 信息结构 | `.factstrip`、`.ledger`、`.archive-door`、表格行、三列事实行 | 统一字段名、内容、动作的网格和长文本策略 |
| 业务元件 | 费用款项、状态徽章、当事人/参与人摘要、期限跑道、时间线 | 复用基础元件，固定业务信息层级 |

页面优先级是：

1. 案件详情页和费用页：问题密度最高，也是截图中两类问题的主要落点。
2. 案件列表、今日页和联系人页：复用同一批列表行、事实条和按钮。
3. 日历、统计、用户中心、登录和分享页：在核心组件稳定后迁移。

## 5. 每个 UI 任务的固定流程

### 第一步：建立问题记录

不要直接把“看起来不齐”交给实现 agent。先写成一条问题：

```text
页面：/case.html
组件：参与人摘要
视口/皮肤：1440×900 / pro
实际：字段名换行后，内容和右侧按钮不在同一垂直中心
期望：字段名、内容、动作沿三列网格对齐，长文本可截断
影响：案件详情页、联系人摘要
证据：截图 + 元素 boundingClientRect
```

### 第二步：判断修复层级

- 多个页面都有同样问题，修共享组件或基础令牌。
- 同一业务结构都有问题，修业务模式组件。
- 只有一个页面的内容顺序有问题，修页面结构。
- 只在某套皮肤出现，检查层 B 是否改变了几何属性；优先修令牌映射，不要给皮肤加独立布局。

### 第三步：写组件契约

在改代码前先写清楚：

- DOM 顺序和网格列；
- 最小/固定高度、内外间距和文本行高；
- 所有状态及状态色；
- 空值、长文本、换行和溢出处理；
- 桌面与 390px 的行为；
- JS 需要的 id、class、data 属性和事件钩子。

### 第四步：实现和迁移

先改共享骨架，再把目标页面迁移到骨架上。层 A 只写布局和信息层级，层 B 只写允许的材质属性。新增的颜色、间距或圆角必须先进入令牌文档，并在同一个变更里补齐三套皮肤。

### 第五步：视觉验收

至少检查以下矩阵：

| 维度 | 值 |
|---|---|
| 皮肤 | `pro`、`paper`、`jade` |
| 视口 | 1440×900、390×844 |
| 内容 | 正常、空值、长中文、长按钮文案、多行标签、错误/禁用状态 |
| 交互 | hover、focus、disabled、展开/收起、弹窗和表单提交 |

验收标准：三皮肤共享布局不发生可见位移；390px 不出现横向滚动；移动端可操作控件高度至少 44px；文字不覆盖、按钮文字垂直居中；重点状态不能因折叠或溢出而消失。

### 第六步：收口

完成时必须同步：

- 组件目录或设计令牌；
- 页面/组件的 QA 记录；
- `docs/CHANGES.md` 中需要公开说明的 UI 行为变化；
- `npm run check` 结果和专用 UI QA 结果。

## 6. 两张示例图的第一批修复方式

### 费用/款项行

把“款项名称、状态、触发节点”拆成固定的网格列。状态标签使用已有 `.chip`/`.pill` 语义，标签内部使用 `inline-flex` 和统一的最小高度；日期和说明是独立字段，不把多个字段拼成一段自然流文本。桌面列宽要对账，移动端改为纵向字段或允许明确截断。

### 当事人/合作参与人摘要

使用 `字段名 / 内容 / 动作` 三列结构。字段名设置最小宽度和明确行高，内容区设置 `min-width: 0`、截断规则和多行策略，右侧动作统一复用 `.btn.small`。每一行用 `align-items: center`，不要依赖按钮默认的行高或页面局部负边距。

这两类修复完成后，应把组件迁移到案件详情、费用、联系人三个页面，避免只修截图所在的一个 DOM。

## 7. 分阶段执行计划

### Phase 0：建立共同语言

- 保留 `DESIGN-TOKENS.md` 和 `style.css` 的双事实约定。
- 新增并维护组件目录。
- 把 UI 问题按页面、组件、严重程度登记。
- 固定一名 agent 作为本轮 UI 规则负责人，其他 agent 通过问题记录提交变更建议。

### Phase 1：核心元件和信息行

- 盘点并锁定 `.btn`、`.chip`、`.pill`、`.panel`、`.row`、`.factstrip`、`.ledger`。
- 修正文字垂直居中、最小触控尺寸、长文本和空值行为。
- 用费用页和案件详情页作为标杆页，完成三皮肤/两视口 QA。

### Phase 2：按页面迁移

- 先迁移案件详情和费用页。
- 再迁移案件列表、今日和联系人页。
- 最后迁移日历、统计、用户中心、登录和分享页。
- 每迁移一个页面，删除该页面已经被共享组件覆盖的旧样式。

### Phase 3：自动护栏

- 把现有 `qa-finance-ui.js` 的矩阵抽成可复用的页面 QA 入口。
- 增加共享检查：横向溢出、控件高度、三皮肤几何差异、常见按钮文字居中和页面 JS 错误。
- 有条件时保存关键页面截图，用 Playwright 做变更前后对比；截图只作为证据，最终仍由组件规则和语义验收决定。

### Phase 4：日常维护

每个新增 UI 任务都先查组件目录，再写问题记录和组件契约。每月集中处理一次重复问题，把页面局部修复提炼回组件；当组件需要破坏旧行为时，记录迁移方式和弃用时间。

## 8. Agent 任务模板

以后可以把下面的模板直接放进每个 UI agent 的任务描述：

```text
目标：
问题记录：
涉及页面：
允许修改：
禁止修改：删除现有 DOM/JS 钩子、发明局部颜色和间距、只在单一皮肤修几何
必须检查：pro/paper/jade；1440px/390px；正常/空值/长文本/禁用态
必须更新：组件目录或 DESIGN-TOKENS.md、QA 证据、必要的 CHANGES.md
完成条件：npm run check 通过，页面无横向溢出，组件契约和实现一致
```

这套流程不要求有 UI 设计师。它把设计师通常负责的四件事拆成可检查的产物：统一规则、组件契约、页面示例和验收证据。agent 可以负责执行和提出方案，但所有方案都要回到同一套令牌和组件契约里。
